    Misc

    • The workflow execution is based on taskflow.
    • The visual graph editor is relying on a python backend with a JavaScript frontend.

    Automated tests (Windows)

    We have a few automated unit tests covering the fundamentals of ayon-workflow. Those are scopped to workflow internal logic, they won't test feature node logic nor any feature coming from other addons.

    .\manage.ps1 runtests

    Develop on the web editor

    The web editor is a separate package that is bundled with the ayon-workflow addon. To develop on the web editor, you need to have an internet connection and npm installed.

    1. Prepare dev bundle

    Setup an AYON dev bundle pointing to the ayon-workflow addon sources.

    2. Build the frontend

    # Build the frontend.
cd ./frontend
# Build the frontend once.
npm run build
# or build the frontend and watch for changes.
npm run dev

    3. Start the editor (backend + frontend)

    '$AYON_EXECUTABLE' --use-dev addon workflow editor

    Multiple platform execution

    For clients working with more than 1 root or platform, some additional steps are required to make the graph execution seamless. The key feature is to define plaftorm-specific path(s) as posix rootless paths. Meaning C:\project_work_root\path\to\your\resource.ext becomes {root[work]/path/to/your/resource.ext} and get resolves by the execution hosts when needed. This needs to happen for the workflow inputs as well as the backend directory.

    Make a rootless Workflow

    To ensure a Workflow can be executed anywhere, you might need some preparation: * store all of the resources inputs as rootless path(s) * handle multi-platform python logic in your custom Plugins * prepare backend directories under the defined AYON project roots.

    All of the vamilla node provided by AYON should be plaftorm-agnostic. If you come up with custom node, you become responsible to handle Windows/Linux/Mac platform support. The execution process leave the inputs untouched, no preflight operation is provided. It's really up to the node execution to detect rootless path(s) and resolve them accordingly. The framework does provide some utility function in ayon_workflow._utils to create/remap rootless path and dataclasses.

    Portable Execution of AYON Workflows

    Successful and portable execution of an AYON Workflow, particularly on rootless systems (like render farms), relies on rigorous path management and code accountability.

    Portability Prerequisites

    Area Key Requirement Scope
    Paths Inputs and resources must bet set as rootless paths (relative to the defined AYON project roots) to avoid OS dependencies. The Workflow author.
    Internal Logic Custom Plugins must integrate the necessary logic to handle platform differences (Windows/Linux/Mac). The Custom Node code.

    [!NOTE]
    "Vanilla" AYON nodes are platform-agnostic. The framework does not modify or pre-process inputs; the rootless path must be resolved dynamically during the node execution itself.

    Execution from a rootless Backend (Renderfarm)

    To submit a Workflow to a rootless backend:

    1. Central Storage: The backend directory must be placed on central storage accessible by all execution hosts.
    2. Submission: The submission command must explicitly include the project_name and the backend path.
    import ayon_workflow

workflow_addon.submit_workflow_to_farm(
    "/path/to/workflow.json",
    "/project_root/path/to/shared/backend",  # must exist and reachable
    project_name="my_project_name"
)

    or

    ayon addon workflow submit \
    --workflow-path /path/to/workflow.json \
    --backend-dir /project_root/path/to/shared/backend \  # must exists and reachable
    --project "my_project_name"

    The generated commands should then be root-agnostic. The root placeholders are resolved on the fly by the Worker to determine the correct absolute path for the executing host.

    ayon addon workflow execute-flow \
    --graph-path {root[type]}/path/to/shared/backend/subgraph.json \
    --backend-dir {root[type]}/path/to/shared/backend/ \
    --slice-flow-id <flow_uuid> \
    --full-flow_id <full_flow_id> \
    --project "my_project_name"
