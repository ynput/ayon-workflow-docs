    Execution Modes

    Overview

    AYON Workflow supports three execution modes, each suited for different use cases:

    Mode Description Persistence Distribution
    In-Memory Run the whole workflow in memory. None Single process
    Backend Run the workflow (all together or in slices) from a persistent backend. Disk Single or Multi process
    Farm Distributed Submit the workflow as job(s) and task(s) managed by a renderfarm. Disk + Farm Multi-machine (usually)

    In-Memory Execution

    The simplest execution mode where the workflow runs directly in memory within a single Python process.

    When to Use

    • Development & Testing: Quick iteration on workflow design.
    • Locally dependent resources: Run from within a DCC host.
    • Lightweight Workflows: Fast-running tasks that complete quickly.
    • Simple Automation: Non-critical tasks without failure recovery needs.

    Advantages: - Fast: No disk I/O overhead. - Simple: Single function call.

    Limitations: - Single Process: Can't distribute across machines. - Memory Bound: Limited by available RAM. - No Checkpointing: Can't pause and resume.

    How It Works

    Workflow → TaskFlow Conversion → Parallel Engine → Results
    1. Your workflow is converted to a TaskFlow Flow object
    2. TaskFlow executes tasks in dependency order
    3. Results are returned directly

    Usage

    From Command Line

    ayon addon workflow execute --workflow-path /path/to/workflow.json

    From Python API

    from ayon_workflow.workflow_editor import Workflow
from ayon_workflow.workflow_execution import execute_workflow

# Load or create workflow
workflow = Workflow.from_json_file("/path/to/workflow.json")

# Execute in-memory
result = execute_workflow(workflow)
print(f"Result: {result}")

    Execution in-memory: Managing the runtime environment

    When a workflow is executed in memory, the python process will inherit the calling environment. The parent code is responsible for providing a workable environment, the execution engine does not enforce any clean-up/reset automatically.

    [!NOTE]
    A common use-case with ayon-workflow is to run a DCC from within another DCC. This is a great example of when an environment clean-up is required!

    To garantee a safe execution in-memory, we recommend to run the graph as a subprocess from a clean environment.

    # I'm within a DCC with totally messed-up environment
from ayon_workflow import env

# Serialize workflow to file
output_workflow = "/path/to/some/workflow.json"
my_workflow.export_to_file(output_workflow)

# "Clean" environment as if I started a new terminal.
clean_env = env.get_clean_envs()

executable_path = os.getenv("AYON_EXECUTABLE")

args = [
    executable_path,
    "addon",
    "workflow",
    "execute",
    "--workflow-path",
    output_workflow
]

if os.getenv("AYON_USE_STAGING") == "1":
    args.insert(1, "--use-staging")
elif os.getenv("AYON_USE_DEV") == "1":
    args.insert(1, "--use-dev")

# Run as if this was called from a fresh terminal through the CLI
# - clean_env = no mess inherited from current env
# - CLI = force re-trigger of the environment by AYON launcher
subprocess.run(args, env=clean_env , check=True)

    Input injection

    Workflow inputs can be dynamically injected through a JSON file at execution time.

    from ayon_workflow import workflow_execution

dynamic_inputs = {
    "NodeName.input_name": some_value,
    "NodeName2.another_input_name": some_other_value,
}

# Just before execution the values coming from dynamic_inputs
# will be injected in the workflow for corresponding node and inputs.
result = execute_workflow(workflow, inputs_data=dynamic_inputs)
print(f"Result: {result}")

    or with CLI:

    ayon addon workflow execute --workflow-path /path/to/workflow.json --inputs-path /path/to/input.json

    Backend-Based Execution

    Execution using a persistent backend (disk-based) that stores task state, inputs, outputs, and metadata. Enables resumable and distributed execution.

    When to Use

    • Multi-process/Multi-host workflow: Workflows that benefit leveraging multiple processes or workers.
    • Failure Recovery: Might need to resume/retry after crashes

    Advantages: - Splitable: A Workflow execution graph might be splitted in multiple executable Flows. This split logic is fully controllable. - Resumable: Each Flow can be retried individually after failures. - Multi-Workers: Each Flow can be run from any workers which has access to AYON executable and the backend.

    Limitations: - Slower: Disk I/O overhead. - Storage: Requires disk space available on persistent storage. - Serialization: Node inputs/outputs must be dataclasses or JSON-serializable.

    How It Works

    Workflow → Flow Split from DispatchGraph -> Register Flow(s) in Backend -> Job Description → Process Flow(s) → Results
    1. Workflow must define at least one dispatch graph
    2. The workflow is split in flow(s) based on a defined dispatch graph
    3. Flows are registered to a shared persistent backend (directory on disk)
    4. Each flow can be processed on its own, reading/writing to backend
    5. State persists between runs

    [!NOTE] We run a custom persistent backend that fixes SMB mount and symlink privileges. If you encounter any issues, you can revert to the Taskflow default by setting AYON_WORKFLOW_USE_LEGACY_BACKEND=1.

    Example: Run a workflow as multiple consecutive command lines

    Step 1: Split and Register Flows to Backend

    from ayon_workflow.workflow_editor import Workflow
from ayon_workflow.workflow_execution.from_backend import to_job_description
from ayon_workflow.plugin_system import register_all_plugins

# Discover all available node definitions
register_all_plugins()

# Load workflow
workflow = Workflow.from_json_file("/path/to/workflow.json")

# Create a dispatch graph within the workflow
dispatch_graph = workflow.create_dispatch_graph("One job with 1 tasks")

# Create one container with all of the execution within it.
generic_container = dispatch_graph.create_node("GenericDispatchTask")
generic_container.node_names = [
    node.name for node in
    workflow.execution_graph.all_nodes
]

# Register to backend directory
backend_dir = "/path/to/backend"
job_description = job_description.to_job_description(
    workflow,
    backend_dir=backend_dir
)

print(f"Registered flows for: {job_description}")

    Step 2: Execute Flows

    for step in job_description.steps:
    args = step.script.args
    result = addon.execute_from_backend(
        # Get command line to run.
        args[5],  # execution graph path,
        args[7],  # backend directory
        args[9],  # slice flow id
        args[11], # full flow id
    )

    or

    ayon addon workflow execute-flow \
    --graph-path /path/to/sub_graph.json \
    --backend-dir /path/to/backend \
    --slice-flow-id <flow_uuid> \
    --full-flow_id <full_flow_id>

    Farm Distributed Execution

    A backend-based execution where workflows are automatically split and submitted across a render farm.

    Requirements

    • A supported renderfarm, configured with AYON (.e.g see ayon-deadline for DeadlineThinkbox)
    • A valid common storage across all workers
    • Properly configured root anatomy if the farm maps different platform/storage

    How It Works

    Workflow → Flow Split from DispatchGraph -> Register Flow(s) in Backend → Job Description → Push Farm Job(s) → Renderfarm Execution
    1. Workflow must define at list one dispatch graph
    2. The workflow execution graph is split in sub-flows based on a provided dispatch graph
    3. Sub-flows are registered to a shared persistent backend (directory on disk)
    4. Job description is created with dependencies
    5. Each job/step from the job description is submitted to the render manager
    6. Farm workers execute sub-flows through backend

    Example: A Blender render job on Deadline Thinkbox

    Step 1: Create a Workflow with a DispatchGraph

    Nodes can be grouped into farm jobs using metadata containers:

    from ayon_workflow.workflow_editor import Workflow, DispatchGraph
from ayon_workflow.plugin_system import register_all_plugins

# Discover all available node definitions
register_all_plugins()

workflow = Workflow("blender_render_on_the_farm")
graph = workflow.execution_graph
blender_node = graph.create_node("BlenderRender")

# TODO: set blender_node with proper input values.

# Create a dispatch graph within the workflow
dispatch_graph = workflow.create_dispatch_graph("One job with 1 tasks")

# Create one task with all of the execution nodes within it.
deadline_job = dispatch_graph.create_node("DeadlineThinkbox")
deadline_job.job_name = "My New Job Name"
deadline_job.pool = "rendering-pool"
deadline_job.group = "render-group"
deadline_job.limit_groups = "blender"
deadline_job.priority" = 50
deadline_job.node_names = [blender_node.name]

workflow.export_to_file("/path/to/workflow.json")

    Step 2: Submit to Farm

    import ayon_workflow

workflow_addon.submit_workflow_to_farm(
    "/path/to/workflow.json",
    "/path/to/shared/farm/backend",  # must exist and reachable
)

    or

    ayon addon workflow submit \
    --workflow-path /path/to/workflow.json \
    --backend-dir /path/to/shared/farm/backend \  # must exists and reachable

    Step 3: Farm Execution

    The system automatically creates job dependencies based on node connections. Each Deadline job runs:

    ayon addon workflow execute-flow \
    --backend-dir /shared/farm/backend \
    --slice-flow-id <flow_uuid> \
    --full-flow_id <full_flow_id>

    [!TIP]
    You can enable full verbosity by setting AYON_WORKFLOW_VERBOSE environment variable to 1 before running the command.

    [!TIP]
    Look at client/ayon_workflow/demo/example_workflow_deadlinethinkbox.py for advanced submission example.

    [!TIP]
    Look at client/ayon_workflow/demo/example_workflow_royalrender.py for submission example with RoyalRender.

    Task Chunking

    For long-duration renders or frame-range-based tasks, it is often necessary to "chunk" the workload across multiple farm nodes (blades). In ayon-workflow, you can manage this distribution using the AbstractDispatchTask.task_chunk attribute.

    Example: Chunked Blender Render on Deadline Thinkbox

    This example demonstrates how to group execution nodes into a single farm job and split it into smaller tasks (chunks).

    Step 1: Configuring the Workflow and Dispatch Graph

    Use metadata containers to group nodes and define your farm parameters (including chunking):

    from ayon_workflow.workflow_editor import (
    Workflow,
    DispatchGraph,
    TaskChunkParameters
)
from ayon_workflow.datatypes import FrameRange
from ayon_workflow.plugin_system import register_all_plugins

# Discover all available node definitions
register_all_plugins()

workflow = Workflow("chunked_blender_render_on_the_farm")
graph = workflow.execution_graph
blender_node = graph.create_node("BlenderRender")

# Define blender render frame range
blender_node["frame_range"] = FrameRange(
    first_frame=1,
    last_frame=5,
)
# TODO: set blender_node with other input values.

# Create a dispatch graph within the workflow
dispatch_graph = workflow.create_dispatch_graph("One job with 1 tasks")

# Create one AbstractDispatchTask with all of the execution nodes within it.
deadline_job = dispatch_graph.create_node("DeadlineThinkbox")
deadline_job.job_name = "My New Job Name"
deadline_job.pool = "rendering-pool"
deadline_job.group = "render-group"
deadline_job.limit_groups = "blender"
deadline_job.priority" = 50
deadline_job.node_names = [blender_node.name]

# Add chunking metadata on the deadline job
deadline_job.task_chunk = TaskChunkParameters(
    node_name=blender_node.name,  # create a chunk based on the blender node
    node_input_name="frame_range",  # create a chunk based on the framerange input
    chunk_size=2,
)

# Submit on the farm
workflow.export_to_file("/path/to/workflow.json")
workflow_addon.submit_workflow_to_farm(
    "/path/to/workflow.json",
    "/path/to/shared/farm/backend",  # must exist and reachable
)

    Best Practices & Requirements

    • Each AbstractDispatchTask has its own specific chunk parameters (no workflow default).
    • Chunking is only supported on FrameRange or ImageSequence inputs.
    • For a AbstractDispatchTask to be chunkable, all of its contained execution nodes must output an ImageSequence. (Nodes such as file uploads or metadata publishing cannot be chunked.)
    • The chunked FrameRange must be explicitly defined at submission time to allow the dispatcher to calculate chunks.

    [!TIP]
    Look at client/ayon_workflow/demo/example_workflow_split.py for an example of submission with chunk.
